# HomeOS v0.1 — Requirements and acceptance checklist

**Status:** Draft for the first implementation milestone

**Source:** [HomeOS project report](../HomeOS_Project_Report.md), especially the v0.1 roadmap entry

**Goal:** An administrator can sign in to a locally deployed HomeOS instance and view current application and runtime status.

## 1. Scope and boundary

v0.1 establishes the Go server, React/TypeScript web app, SQLite persistence, administrator authentication, and a small monitoring dashboard. It should run on the target Windows/Docker homelab and remain portable to Linux.

The report's roadmap assigns HomeDrive to v0.2, although its conclusion mentions Drive in the first milestone. This specification follows the versioned roadmap: v0.1 includes only the storage needed for configuration, users, and sessions. File uploads, shared storage, media, Docker control, host command execution, backups, and AI are later work.

Only one administrator account is required for v0.1. The data model should allow more users later, but self-registration, invitations, password recovery, and role management are outside this milestone.

## 2. User journeys

1. **Initial setup:** The operator configures a data directory, starts the server, applies database migrations, and creates the first administrator using a local command that prompts for the password without echoing it. Startup must not create a known default credential.
2. **Sign in:** The administrator opens the web app, signs in, and reaches the dashboard. Invalid credentials return a generic error.
3. **View status:** The dashboard shows the app's health, version/build identifier, last successful refresh, and available CPU, memory, and disk measurements. Every measurement identifies what it covers: `host`, `container`, or `application`. Unsupported measurements show “Unavailable” with a reason, never a fabricated zero.
4. **Sign out:** The administrator signs out; the session is invalidated server-side and the dashboard is no longer accessible.
5. **Failure:** If a status source fails, the dashboard remains usable and marks that measurement stale or unavailable. A broken database or migration prevents readiness from reporting healthy.

## 3. Functional requirements

| ID | Requirement | Acceptance evidence |
|---|---|---|
| CORE-01 | The Go server starts from documented configuration and serves the built web app and versioned API from one origin. | Fresh setup reaches the sign-in page without a separate production Node server. |
| CORE-02 | Database migrations run predictably against a configured SQLite file. Startup fails visibly on migration error. | New database initializes; a migration failure makes readiness fail. |
| AUTH-01 | A local bootstrap command creates the first administrator; no web-based public registration exists. | No default password; duplicate bootstrap attempt is rejected. |
| AUTH-02 | Passwords are stored using a maintained password hashing implementation with a per-password salt; plaintext passwords are never persisted or logged. | Database inspection finds no plaintext password; authentication tests pass. |
| AUTH-03 | Successful sign-in creates an opaque, revocable server-side session in an `HttpOnly`, `SameSite` cookie; use `Secure` when served over HTTPS. | Cookie flags and logout invalidation are verified. |
| AUTH-04 | Protected API routes require a valid session, and state-changing browser requests have CSRF protection. | Unauthenticated requests return 401; invalid CSRF requests are rejected. |
| AUTH-05 | Login attempts have a bounded rate limit and generic failure response. | Repeated invalid attempts are throttled without revealing whether an account exists. |
| UI-01 | The responsive web app has sign-in, dashboard, loading, error, and sign-out states. | Desktop and mobile viewport checks pass. |
| MON-01 | The server exposes liveness and readiness separately. Readiness checks the database and required startup state. | Health endpoints return expected results during normal operation and database failure. |
| MON-02 | The authenticated dashboard displays application health and only those runtime metrics the deployment can actually observe. | Each metric has a scope, unit, timestamp, and available/stale/unavailable state. |
| MON-03 | Status refreshes automatically at a modest interval and can be refreshed manually. | A new sample appears without a full page reload; failure does not blank the dashboard. |
| OPS-01 | Configuration, startup, data persistence, and backup of the SQLite file are documented for a local deployment. | A second operator can follow the instructions on a clean machine. |

For v0.1, monitoring is **read-only**. The initial Docker deployment may see container metrics rather than Windows host metrics. Showing host-wide Windows metrics requires a later restricted host agent; the UI must label this distinction clearly.

## 4. Preliminary API contract

All API responses use JSON except `204` responses. Errors use a stable shape such as `{ "error": { "code": "...", "message": "..." } }`. Exact response fields can be refined during implementation, but changes to them require updating this document and API tests.

| Method and path | Access | Purpose |
|---|---|---|
| `GET /api/v1/health/live` | Public | Process liveness; no sensitive details. |
| `GET /api/v1/health/ready` | Public | Readiness; `503` when required startup state or database is unavailable. |
| `POST /api/v1/auth/login` | Public, rate limited | Accept username and password; establish session. |
| `POST /api/v1/auth/logout` | Authenticated + CSRF | Revoke current session; return `204`. |
| `GET /api/v1/auth/me` | Authenticated | Return current user's ID, display name, and role. |
| `GET /api/v1/status` | Authenticated | Return app status and an array of scoped metric samples. |

`GET /api/v1/status` should include sample time and source scope for each metric. Use standard HTTP statuses (`400` malformed input, `401` unauthenticated, `429` throttled, `503` unavailable dependency). Public health endpoints must not reveal filesystem paths, account names, or infrastructure details.

## 5. Initial data and module boundaries

Minimum SQLite records:

- `schema_migrations`: applied migration versions.
- `users`: ID, username, display name, password hash, role, created/updated times, disabled flag.
- `sessions`: opaque token hash, user ID, created/expiry/revocation times. Store a hash of the cookie token, not the token itself.

The `core` owns configuration, migrations, authentication, sessions, and authorization. The `monitor` module gathers read-only status samples through an interface so the runtime source can differ by deployment. The API layer translates these services into HTTP responses. The frontend only consumes the API; it never reads the database or host resources directly.

The v0.1 permission rule is simple: public access to liveness/readiness and login; authenticated administrator access to `/auth/me`, `/auth/logout`, `/status`, and the dashboard. Authorization must be checked server-side on every protected request.

## 6. Deployment and security constraints

- Default to binding on loopback for native development. Document the explicit configuration needed for LAN access; do not expose v0.1 directly to the public Internet.
- For remote access, use a private access path such as the existing Tailscale setup and HTTPS at the access boundary.
- Keep the SQLite database and all secrets outside the Git repository and outside public web assets.
- Use least-privilege filesystem access for the application data directory. Do not mount the Docker socket or grant host command execution for v0.1.
- Define session expiry and password-hash parameters during implementation using current maintained-library guidance; record the selected values in deployment documentation.
- Do not log passwords, session tokens, CSRF tokens, or full authentication request bodies.

## 7. Suggested implementation sequence

1. Create the Go server, frontend build, configuration, and SQLite migration skeleton.
2. Implement liveness/readiness and one status sample end to end: collector → API → dashboard. Label its scope clearly.
3. Add bootstrap admin, password hashing, sessions, authorization, CSRF protection, and login throttling.
4. Complete the sign-in/dashboard/sign-out UI and additional available metrics.
5. Package the Docker deployment and document setup, persistence, backup, and failure recovery.

## 8. Release acceptance checklist

- [ ] On a clean Windows/Docker setup, the documented procedure starts HomeOS and preserves its SQLite data across container restarts.
- [ ] An operator can create the first administrator locally without placing a password in shell history or a committed file.
- [ ] Correct credentials open the dashboard; incorrect credentials do not disclose account existence and are rate limited.
- [ ] Unauthenticated callers cannot read status or current-user data; logout invalidates the session immediately.
- [ ] The dashboard shows application health and at least one real, labeled runtime metric with units, scope, and sample time.
- [ ] A missing metric is visibly unavailable; a failed refresh does not silently show old data as current.
- [ ] Liveness and readiness behave differently when the database is unavailable.
- [ ] The app works at desktop and mobile widths and shows usable loading/error states.
- [ ] A fresh database and an existing database both start successfully; migration failure is explicit.
- [ ] Automated tests cover authentication, access control, session revocation, health behavior, and status serialization; the frontend build and backend tests pass.
- [ ] Documentation explains configuration, network exposure, SQLite backup/restore, and how to recover administrator access without a default credential.

The performance figures in the project report are targets to measure, not release gates until the test environment and workload are specified.
